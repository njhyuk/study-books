# 싱크 어게인 8장. 격앙된 대화

> 갈등이 지지부진하게 이어질 때는 복잡성이 돌파구를 열어준다. - 아만다 리플리

뜨거운 쟁점을 두 편으로 나누면 대화가 막히고, 여러 갈래로 쪼개 보여주면 풀린다는 장이다. 복잡성을 전하는 방법(경고성 일러두기, 만약의 경우, 여러 해결책)과 감정을 다양하게 드러내는 법을 다룬다.

## 어려운 대화 연구소의 총기 규제 기사 실험
- 낙태 문제로 의견이 반대인 두 사람이 20분 안에 공동성명서를 쓰는 실험이다. 그 전에 총기 규제 기사를 읽게 했다.
  - 찬반 양쪽을 나란히 다룬 기사: 44%만 합의했다.
  - 여러 관점이 얽힌 복잡한 문제로 다룬 기사: 100% 합의했다.
- 반대편 의견을 보여주는 것만으로는 안 바뀐다. 두 극단을 보면 오히려 내 의견이 굳는다.
- 이렇게 세상을 둘로 나누려는 성향이 **이분법 편향**이다. 해독제는 쟁점을 복잡하게 보여주는 것이다.
- 책의 결론: 두 극단을 나란히 놓는 건 양극화의 일부다. 단순화하려는 충동에 저항하는 것이 더 많은 주장을 접하는 첫걸음이다.
- 예시: "AI 코딩 도구 도입 찬성이냐 반대냐"보다 "테스트 코드엔? 결제 로직엔?"으로 쪼개면 서로 동의하는 칸이 생긴다.
- 포인트: 쟁점을 두 편으로 나누지 말고 여러 갈래로 쪼개라.

## 불편한 진실 몇 가지
- 앨 고어의 <불편한 진실> 이후에도 미국인의 기후변화 믿음은 거의 안 바뀌었다. 고어는 "진실 대 부정론자" 구도를 썼고, 편을 고르라고 하면 중간에 있던 사람은 반대쪽으로 간다.
- 실제 여론은 둘이 아니라 여섯 갈래다(놀람 31%, 걱정 26%, 조심 16%, 무관심 7%, 의심 10%, 묵살 10%). 그런데 묵살하는 10%가 미디어에 가장 많이 나온다.
- 회의론자(질문하며 생각을 고침)와 부정론자(결론을 지키려 사실을 무시함)는 다르다.
- **해결책 혐오**: 해결책이 싫으면 문제 자체를 부정한다. 해결책을 여러 개 보여주면 "왜 문제냐"에서 "어떻게 하냐"로 대화가 옮겨 간다.
- 같은 커피 논문으로 "뇌에 좋다", "뇌에 해롭다" 기사가 동시에 나왔다. 불확실성을 인정한 기사가 오히려 신뢰를 잃지 않는다.
- 책의 결론: 고어의 문제는 열정이 아니라 '우리 대 저들' 구도였다. 스펙트럼 전체를 보여줘야 중간에 있던 다수가 행동할 준비를 한다. 정보를 만들 때는 불확실성을 인정해도 신뢰를 잃지 않는다.
- 예시: "기술 부채 갚으려면 한 분기 멈춰야 해요"라고 하면 PO는 "그게 그렇게 심각해요?"라며 문제부터 부정한다.
- 포인트: 상대가 문제를 부정하면 해결책이 싫은 건 아닌지 보고, 해법을 여러 개 꺼내라.

## 몇 가지 경고성 일러두기와 만약의 경우
- **경고성 일러두기**: 결론에 한계를 함께 밝힌다. "연구가 더 필요하다" 한 줄만 붙여도 사람들이 더 관심을 갖고 마음을 연다.
- **만약의 경우**: 언제, 어디서, 누구에게 결과가 달라지는지 밝힌다. "다양성은 좋다"보다 "좋지만 쉽지는 않다"가 더 설득력 있었다.
- 정서지능 논쟁은 글쓴이가 정확한 기록보다 이야기의 일관성에 빠지는 함정의 사례다. 골먼은 "성공의 90%", 피터슨은 "그런 건 없다"고 했다. 실제로는 감정을 다루는 직무에서만 도움이 되고 IQ가 두 배 이상 중요하다.
  - 저자의 진단: 둘 다 핵심을 놓쳤다. "의미가 있나 없나"가 아니라 "언제 중요한가"를 물어야 한다.
  - 저자는 이 장의 지침(미묘한 차이, 일러두기, 만약의 경우)을 지켜 링크드인에 글을 올렸다. 많은 사람이 열정적으로 반응했고, 일부는 증거를 보지 않고 적개심을 드러냈다(아이디어 숭배 집단).
- 책의 결론: "◇◇는 항상 옳다"고 단정하는 순간 아이디어 숭배 집단이 된다. 어떤 행동도 언제나 효과적이지는 않고 모든 처방은 의도하지 않은 결과를 낳는다. 그러니 결론을 모르는 채로 방법만 보고 연구를 판단하라(존 롤스의 무지의 장막).
- 예시: "캐시 붙여서 3배 빨라졌어요"보다 "읽기 API에서만 3배, 쓰기 쪽은 아직 측정 안 했어요"가 더 믿음을 준다.
- 포인트: 결론을 말할 때 "아직 모르는 것" 한 줄과 "이 경우에만" 한 줄을 붙여라.

## 복합적인 감정
- "상대 입장이 돼 보라"는 조언은 실험에서 실패했다. 상상은 틀리기 쉽다. 상상하지 말고 직접 물어라(관점 탐색).
- 감정을 빼야 대화가 잘 된다는 것도 틀렸다. 상대가 그 문제에 진심이라는 게 보이면 오히려 더 믿게 된다. "원칙을 지키는 모습을 존경한다"로 시작하면 상대가 더 너그러워진다.
- 안 풀리는 대화는 감정이 한두 개(분노, 짜증)에 갇혀 있다. 잘 풀리는 대화는 화, 호기심, 불안, 흥분, 깨달음의 기쁨이 오르내린다.
- 크리스천 쿠퍼 사건: 공원에서 개 목줄을 채워 달라고 한 흑인 남성을 백인 여성이 경찰에 거짓 신고했다. 여성은 "나는 인종차별주의자가 아니다"라고 단순하게 사과했다. 크리스천은 "사과는 진심인 것 같지만, 인종차별주의자인지는 그녀만 답할 수 있다"며 섞인 판단을 했다.
  - 왜 나오나: 쟁점처럼 사람도 "인종차별주의자냐 아니냐" 두 칸으로 나눌 수 없다는 것, 섞인 감정을 드러낸 크리스천이 지켜보는 사람들까지 다시 생각하게 했다는 것을 보여준다.
  - 책의 결론: 다시 생각하는 책임은 피해자가 아니라 가해자에게 있다. 여성이 자기 믿음과 행동을 다시 돌아봤다면 다른 사람들의 모범이 됐을 것이다.
- 장의 마무리: 전도사, 검사, 정치인에게 복잡성은 불편한 진실이지만, 과학자처럼 생각하면 이해와 발전의 기회가 된다.
- 책의 결론: 다시 생각하기를 막는 건 감정 표현이 아니라 감정이 한두 개로 좁아지는 것이다. 상대 마음은 상상하지 말고 물어서 찾는다.
- 예시: 리뷰에서 "세 번째 반려라 지치는데, 그 원칙이 왜 중요한지는 진짜 궁금해요"라고 말하면 대화가 이어진다.
- 포인트: 상대 마음을 짐작하지 말고 묻고, 내 감정은 섞인 그대로 말하라.

## 개발자 시나리오 시뮬레이션

아래는 8장 개념을 개발 현장에 대입해 본 가상 시나리오다. 실제 사례가 아니다.

### 시나리오 1. AI 코딩 도구 도입 대 금지 (이분법 쪼개기)
- 책 사례: 어려운 대화 연구소의 총기 규제 기사 실험. 찬반 두 극단 기사는 합의 44%, 여러 관점 기사는 100%. 찬반 투표를 작업별 칸으로 쪼개는 장면으로 옮겼다.
- 상황: 회의에서 도입파와 금지파가 맞선다.
- 흔한 대응 (실패)
  - 진행자: "찬반 투표로 정하죠."
  - 결과: 도입으로 정해지지만 금지파는 리뷰마다 반대 코멘트를 단다.
- 책 방식으로 바꾸면
  - 쪼개기 / 진행자: "도입이냐 금지냐 말고, 테스트 코드, 결제 로직처럼 작업별로 보면 어떠세요?"
  - 금지파: "나눠도 결국 쓰자는 얘기잖아요."
  - 반영 / 진행자: "결국 다 열리게 될까 봐 걱정되시는 거네요."
  - 금지파: "네. 한번 열면 결제 코드까지 들어가요. 외부 라이브러리도 그렇게 퍼졌고요."
  - 관점 탐색 / 진행자: "그때 뭐가 있었으면 안 퍼졌을까요?"
  - 금지파: "어디까지 쓰는지 선이요. 테스트 코드 정도는 저도 괜찮아요."
  - 요약 / 진행자: "선이 있어야 하고, 테스트 코드는 괜찮다는 거죠. 선 긋는 초안은 누가 써 볼까요?"
  - 금지파: "제가 써 볼게요. 어디까지 열지는 아직 모르겠지만요."
- 왜 통하나: 쟁점을 칸으로 쪼개자 동의하는 칸이 보였고, 반대하던 사람이 선을 긋는 역할을 맡았다.

### 시나리오 2. "원인 확실해요?"라는 다른 팀 리드 (경고성 일러두기, 만약의 경우)
- 책 사례: 커피 기사와 저자의 정서지능 글. 불확실성을 인정해도 신뢰를 잃지 않았고, 저자는 일러두기와 만약의 경우를 붙여 글을 썼다. 장애 원인 보고에 "아는 것 / 모르는 것 / 이 조건에서만"을 붙이는 장면으로 옮겼다.
- 상황: 장애 회고에서 연동 팀 리드 G가 "저번에도 확실하다더니 또 났잖아요"라고 묻는다.
- 흔한 대응 (실패)
  - 개발자: "이번엔 확실합니다. 커넥션 풀 문제였어요."
  - 결과: 2주 뒤 다른 원인으로 재발하고 G는 이 팀 보고를 안 믿게 된다.
- 책 방식으로 바꾸면
  - 일러두기 / 개발자: "확인된 건 커넥션 풀 고갈까지예요. 왜 그때 몰렸는지는 아직 몰라요."
  - G: "결국 모른다는 거네요."
  - 반영 / 개발자: "저번 일 때문에 이번 보고도 믿기 어려우신 거죠."
  - G: "네. 그거 믿고 재시도 로직 뺐다가 우리도 같이 터졌어요."
  - 만약의 경우 / 개발자: "평소 트래픽에선 재발 안 하는 걸 확인했고, 배치 시간대는 아직이에요. 어떤 정보가 있으면 재시도 로직을 정하실 수 있을까요?"
  - G: "위험한 시간대만 알면 그때 재시도를 켜 둘 수 있죠."
- 왜 통하나: 아는 것과 모르는 것을 나눠 말하자 오히려 신뢰가 생겼다.

### 시나리오 3. 기술 부채가 문제없다는 PO (해결책 혐오)
- 책 사례: 해결책 혐오 실험. 총기 규제 글을 읽은 자유주의자는 침입자 폭력 문제를 묵살했고, 보수주의자는 탄소 감축보다 녹색 기술에 호응했다. "한 분기 중단"이 싫어 기술 부채를 부정하는 PO 장면으로 옮겼다.
- 상황: 배포마다 장애 나는 모듈이 있다. 개발팀이 "한 분기 멈추고 다시 짜자"고 하자 PO H는 "그렇게 문제인가요?"라고 한다.
- 흔한 대응 (실패)
  - 리드: "장애 로그 보세요. 안 고치면 계속 터집니다."
  - 결과: 증거를 들이밀수록 H는 문제를 작게 본다. 싫은 건 문제가 아니라 '한 분기 중단'이다.
- 책 방식으로 바꾸면
  - 진짜 궁금함 / 리드: "이 모듈 얘기 나올 때 제일 걸리는 게 뭐예요?"
  - H: "개발팀은 고치자 할 때마다 다 멈추자고 하잖아요."
  - 반영 / 리드: "고치자는 말이 로드맵을 멈추자는 말로 들리셨군요."
  - H: "지난번에 석 달 날리고 출시 약속 다 어겼어요. 제가 사과했고요."
  - 여러 해법 / 리드: "방법이 하나는 아니에요. 스프린트마다 20%만, 장애 잦은 함수 두 개만, 기능 넣을 때 그 부분만. 덜 부담되는 게 있을까요?"
  - H: "20%면 생각은 해 볼게요. 출시 약속만 안 깨지면요."
- 왜 통하나: 해법을 여러 개 펼치자 "왜 문제냐"가 "어떻게 하냐"로 바뀌었다.

### 시나리오 4. 세 번째 반려된 PR (존중, 관점 탐색, 섞인 감정)
- 책 사례: 존중 표현 실험과 피터 콜먼의 감정 연구. "원칙을 지키는 당신을 존경한다"로 시작하면 더 관대해졌고, 상상 대신 묻기, 섞인 감정이 대화를 살렸다. 원칙으로 PR을 반려하는 시니어와의 대화로 옮겼다.
- 상황: 시니어 I가 "도메인 레이어에 프레임워크 코드 금지" 원칙으로 주니어 J의 PR을 세 번째 반려했다.
- 흔한 대응 (실패)
  - J: "그 원칙 과한 것 같아요. 다른 팀은 다 써요."
  - I: "원칙은 원칙이야."
- 책 방식으로 바꾸면
  - 존중, 섞인 감정 / J: "원칙 지키시는 건 배우고 싶어요. 솔직히 세 번째라 지치기도 하는데, 왜 중요한지는 진짜 궁금해요."
  - I: "그냥 깔끔하게 하자는 거야."
  - 관점 탐색 / J: "예전에 이 원칙이 없어서 고생하신 적 있으세요?"
  - I: "프레임워크 업그레이드 때 도메인 코드까지 다 뜯었어. 두 달 걸렸지."
  - 반영 / J: "그 두 달을 다시 안 겪으려는 거군요."
  - I: "그렇지. 코드 길어지는 건 나도 알아."
  - 배우는 질문 / J: "그럼 꼭 지켜야 할 선은 어디라고 보세요?"
  - I: "어노테이션은 봐줄게. 프레임워크 타입이 메서드 시그니처에 들어오는 것만 막자."
- 왜 통하나: 원칙의 옳고 그름 대신 원칙 뒤의 경험을 물었고, 선은 I가 직접 정했다.

### 시나리오 5. "AI가 짜는데 코드리뷰가 필요해요?" (만약의 경우)
- 책 사례: 정서지능 논쟁. 골먼은 "성공의 90%", 피터슨은 "그런 건 없다"고 단정했지만 저자는 "있냐 없냐"가 아니라 "언제 중요한가"를 물어야 한다고 했다. "코드리뷰와 가독성이 필요하냐"를 "어떤 코드에서 필요하냐"로 바꾸는 장면으로 옮겼다.
- 상황: AI 도구를 적극 쓰는 팀원 P가 "AI가 짜고 AI가 읽는데 가독성 리뷰는 시간 낭비"라며 리뷰를 없애자고 한다.
- 흔한 대응 (실패)
  - TL: "리뷰는 필수예요. 가독성은 기본이고요."
  - 결과: "필요하다 대 필요 없다"만 남고 회의가 끝난다.
- 책 방식으로 바꾸면 (어떤 코드인지에 따라 답이 다르다)
- **기준이 아직 없을 때**
  - 진짜 궁금함 / TL: "리뷰가 시간 낭비라고 느낀 PR이 어떤 거였어요?"
  - P: "네이밍 하나로 하루씩 붙잡히잖아요. AI한테 시키면 5분인데. 읽는 것도 AI가 설명해 주고요."
  - 반영 / TL: "5분이면 되는 걸 리뷰 기다리느라 하루 쓰는 게 답답하신 거네요."
  - P: "네. 솔직히 리뷰가 그냥 통과 의례 같아요."
  - 반대쪽 묻기 / TL: "반대로, AI가 짠 코드 때문에 곤란했던 적은 없어요?"
  - P: "…지난달 정산이요. 경계값이 틀렸는데 아무도 못 봤어요."
  - 만약의 경우, 일러두기 / TL: "그럼 '리뷰가 필요하냐'보다 '어떤 코드에 필요하냐'로 나눠 보면요? 저도 AI가 읽기를 어디까지 대신할지는 몰라요."
  - P: "정산처럼 돈 나가는 데는 사람이 봐야죠. 어드민 화면 같은 건 빼도 되고요."
  - 요약 / TL: "네이밍으로 하루씩 붙잡히는 게 문제고, 돈 나가는 데는 사람이 보고 어드민은 빼자는 거죠. 기준 초안 써 보시고 한 달 뒤에 다시 볼까요?"
  - P: "써 볼게요. 대신 네이밍 코멘트는 빼 주세요."
  - 열쇠: "필요하냐"를 "어떤 코드에 필요하냐"로 바꾸고, 그 기준을 상대가 쓰게 한다.
- **돈, 데이터가 걸린 코드**
  - 진짜 궁금함 / TL: "이번 결제 재시도 PR도 리뷰 없이 가자는 거예요? 어떤 이유에서요?"
  - P: "AI가 테스트까지 짰어요. 다 통과했고요."
  - 반영 / TL: "테스트까지 통과했는데 또 붙잡히면 억울하죠."
  - P: "네. 사람이 보면 또 네이밍 얘기만 할 거잖아요."
  - 반대쪽 묻기 / TL: "정산 때도 테스트는 있었는데, 왜 못 잡았을까요?"
  - P: "…테스트도 AI가 짜서, 같은 데를 똑같이 잘못 이해했어요."
  - 만약의 경우 / TL: "그럼 이런 코드는 리뷰를 하되, 무엇을 볼지를 바꾸면 어때요?"
  - P: "네이밍 말고 경계값이랑 중복 결제만 보는 체크리스트면 받을게요."
  - 요약 / TL: "테스트도 같은 오해를 할 수 있으니 돈 나가는 코드는 사람이 보고, 대신 네이밍이 아니라 경계값과 중복 결제만 본다는 거죠."
  - 열쇠: 리뷰를 할지 말지가 아니라 무엇을 볼지를 바꾼다. 여기선 가독성보다 정확성이다.
- **한 번 쓰고 버리는 코드**
  - P: "이번 주 데이터 정리 스크립트도 리뷰 올려야 해요? 한 번 돌리고 지울 건데."
  - 진짜 궁금함 / TL: "한 번 돌리고 지운다는 건 어디까지 확인된 거예요?"
  - P: "운영 DB엔 안 붙고 스테이징 리포트만 뽑아요. 결과는 제가 직접 확인하고요."
  - 반영 / TL: "결과를 눈으로 확인하니까 코드를 다시 읽을 일은 없다는 거네요."
  - P: "네. 이걸로 하루 기다리면 리포트가 늦어요."
  - 만약의 경우 / TL: "그럼 리뷰는 빼죠. 다만 운영 DB에 붙거나 두 번 이상 돌리게 되면 그때는 올려 주세요. 그 선, P님이 보기엔 어때요?"
  - P: "그 정도면 괜찮아요. 스크립트 맨 위에 그 조건 적어 둘게요."
  - 열쇠: 다시 읽을 일 없고 결과로 검증되는 코드라면 리뷰를 빼는 게 맞다. 대신 언제 리뷰로 돌아오는지 조건을 정해 둔다.
- 왜 통하나: 정답은 하나가 아니다. 저자가 정서지능에서 "있냐 없냐"가 아니라 "언제 중요한가"를 물은 것처럼, 리뷰도 "필요하냐"가 아니라 "어떤 코드에서"를 묻는다. 어느 쪽이든 조건은 상대가 정하게 했다.
